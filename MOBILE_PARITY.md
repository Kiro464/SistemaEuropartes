# EuropartesSystem — cobertura funcional web y Android

Matriz de control para que cada fase Android implemente todas las operaciones aplicables a cada rol, usando los permisos y reglas del backend como autoridad. Esta matriz se basa en inspección estática del backend, frontend y código Android; no vuelve a ejecutar las pruebas funcionales históricas.

## Estados y reglas de lectura

- **Implementado y validado por el usuario**: el usuario confirmó la operación en la fase indicada; no significa que Codex la haya probado en esta intervención.
- **Implementado; validación pendiente**: existe código Android, pero no hay confirmación funcional registrada para esta operación concreta.
- **Parcialmente implementado**: solo parte de las acciones o estados del recurso están en Android.
- **Pendiente**: no existe aún la funcionalidad Android prevista.
- **No disponible mediante endpoint identificado**: no se identificó una operación API independiente; no simularla localmente.
- **No determinado**: la evidencia inspeccionada no establece una regla o contrato.

Roles abreviados: **AG** Administrador General; **AF** Asesor Financiero; **V** Vendedor; **STI** Soporte TI; **AM** Asesor de Marketing; **CL** Coordinador de Logística; **OL** Oficial de Logística. Los roles enumerados son los autorizados en el backend para esa operación. Una restricción de UI web no concede permiso al servidor.

## Discrepancias y límites conocidos

1. La web expone `#/solicitudes-compras` a AG, AF, V, CL y OL, porque agrupa solicitudes y compras. El endpoint de solicitudes permite V y CL, mientras el de compras permite AG, AF, CL y OL. La matriz y Android deben filtrar por recurso/acción; Django conserva la autoridad.
2. La vista de despachos pendientes aparece duplicada en el backend según auditoría Fase 2/4/7. La matriz refleja el permiso OL identificado y no intenta corregir esa implementación.
3. El dashboard consulta el DW y su refresco depende del ETL; no se afirma que una transacción operacional aparezca inmediatamente en reportes.
4. Reservas y movimientos manuales no se representan como CRUD local sustituto. Se originan en flujos comerciales del servidor; sin endpoint independiente, Android no debe fingir una operación confirmada.
5. Las operaciones CRUD aceptadas por los serializers no garantizan que cualquier registro pueda borrarse: relaciones protegidas, estado y validaciones pueden rechazarlo. La interfaz debe mostrar la respuesta real.
6. “No determinado” significa evidencia insuficiente, no una denegación.

## Actualización obligatoria en fases Android

Antes de implementar una fase: verificar las filas del módulo para **cada rol** y **cada operación**, contrastando backend (permiso, método, estado y reglas), frontend (acción visible/flujo) y Android (código y validación). No inferir permiso de la ruta visual.

Al cerrar una fase: actualizar estado y fase en esta matriz; distinguir revisión estática, compilación y validación funcional del usuario. Añadir las pruebas de aceptación específicas y registrar cualquier operación omitida con su fase o con “No disponible mediante endpoint identificado”. No dar por cerrada una fase por lectura solamente si el criterio requiere interacción funcional.

Hoja de ruta: **Android 8** movimientos y Kardex; **Android 9** solicitudes, compras y proveedores; **Android 10** ventas, facturación, clientes, reservas y despacho; **Android 11** usuarios y administración; **Android 12** dashboard e informes; **Android 13** sincronización offline-first; **Android 14** integración, regresión y entrega. Las fases de auditoría/rediseño 1–7 constan como realizadas; la matriz marca expresamente las acciones móviles aún pendientes.

### Discrepancias y límites de cobertura

- `Frontend/js/views/ventas/ventasService.js` conserva un comentario de payload obsoleto con `empleado_id`; `CrearFacturaSerializer` confirma que el backend espera solamente `cliente_id` y `productos[{producto_id,cantidad}]`, y `GenerarFacturaView` deriva empleado de la sesión.
- `Backend/apps/movimientos/venta/views.py` declara dos veces `DespachosPendientesAPIView`; la última definición es la que Python enlaza al import en `urls.py`. No se modificó el backend.
- No existe endpoint independiente de consulta/alta/liberación de reservas identificado; se documentan como efecto de factura y despacho.
- La política del backend permite que cantidad cero sea omitida por línea en despacho parcial. Android requiere al menos una línea positiva para evitar confirmar una operación vacía.
- La web ofrece alta de cliente desde un modal del POS; Android reutiliza el destino Clientes y el selector de clientes del POS, por lo que la misma operación existe pero el recorrido es distinto. La búsqueda de producto en POS filtra localmente el catálogo activo recuperado.
- La web guarda la preferencia NIO/USD en `localStorage` (`Frontend/js/core/state.js`), muestra `C$` o `$` y, al elegir USD, divide los importes visualizados por el `tipo_cambio` devuelto por `GET /movimientos/venta/configuracion/`. Android aplica el mismo criterio de presentación en el POS y el historial/detalle, guarda únicamente la preferencia visual localmente y usa la tasa actual de esa configuración. No modifica importes de DTO/payload ni los cálculos o la factura definitivos de Django; sin una tasa positiva no habilita el cambio a USD.
- El usuario informó que realizó las pruebas manuales de las Fases 9 y 10, corrigió los errores de compilación encontrados y confirmó que el ajuste monetario posterior de Android 10 funciona. Esta revisión no volvió a ejecutar pruebas; no se atribuyen a Codex compilaciones ni pruebas funcionales.

La web consume 17 solicitudes para sus paneles. El endpoint real `GET /reportes_dw/dashboard/stock-critico/` calcula stock sobre snapshots del DW, pero la web no lo utiliza: su stock crítico actual se deriva del catálogo operacional. Por ello Android replica el comportamiento de la web y no mezcla ambas fuentes. También existen `resumen`, `solicitudes-por-empleado`, `stock-historico` y `stock-resumen` en las rutas backend, pero la web dashboard inspeccionada no los consume; quedan fuera de esta paridad visual y no se presentan como paneles móviles.

La preferencia NIO/USD reutiliza el almacén visual existente y el tipo de cambio de `GET /movimientos/venta/configuracion/`. Solo transforma la presentación numérica; no modifica valores de respuesta ni cálculos de Django. Los informes mensuales que el servicio web llama sin `rango` se mantienen sin ese filtro en Android. El selector temporal usa los valores visibles en la web; no añade filtros arbitrarios.
